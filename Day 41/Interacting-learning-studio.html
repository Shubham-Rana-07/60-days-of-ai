Module 1 · Beginner

Reading the Mess

⏱ 15 min 🎯 Diagnose messy data before touching it

Before you fix anything, you have to see it clearly. Most cleaning mistakes come from skipping inspection and jumping straight to .dropna() or .fillna(0) without understanding what's actually wrong. This module builds your diagnostic toolkit.

Analogy — Think of a new dataset like a patient arriving in triage. You don't start treatment before checking vitals: temperature, pulse, symptoms. df.info(), df.isnull().sum(), and df.duplicated().sum() are your vitals check for data.

Core Inspection Toolkit
# Shape and structure
df.shape                  # (rows, columns)
df.info()                 # dtypes + non-null counts per column
df.head(), df.tail()      # peek at real rows

# Where is the damage?
df.isnull().sum()         # missing values per column
df.duplicated().sum()     # exact duplicate rows
df.describe(include='all')# quick stats, catches weird min/max
df.dtypes                 # is "price" really a number, or text?
Three problems, one table: a near-duplicate row, missing + inconsistently formatted values, and a number stored as text.
Comparisons
SymptomWhat it looks likeMethod that reveals it
Missing valuesNaN, None, empty string, "N/A", "-"isnull().sum()
Duplicate rowsSame row twice, or same entity with casing/whitespace differencesduplicated()
Wrong dtypeNumbers stored as text, dates stored as stringsdtypes, info()
Inconsistent categories"NY", "ny", "New York" all meaning the same thingvalue_counts()
Practical Exercise
Try it yourself

You load a CSV and run df.dtypes. The order_total column shows object instead of float64. What's the most likely explanation, and what's your first diagnostic step?

Most likely: at least one row contains a non-numeric value in that column — a stray currency symbol ("$19.99"), a thousands separator ("1,200"), or a text placeholder ("N/A"). First step: run df['order_total'].str.extract(r'([^0-9.]+)') or simply eyeball df['order_total'].unique() on a sample to find the offending characters before converting with pd.to_numeric(..., errors='coerce').

Common Misconceptions
✕"NaN and an empty string are the same thing." They're not — '' is a valid (if unhelpful) string value, while NaN is a float marking true absence. isnull() won't catch empty strings.
✕"Duplicates means identical rows." Real-world duplicates often differ by casing, whitespace, or formatting — you must normalize before comparing.
✕"read_csv() always infers the right dtype." It infers based on the whole column; one bad row silently downgrades an entire numeric column to object.
Key Takeaways
  • Always inspect before you clean: shape, dtypes, nulls, duplicates, and a sample of rows.
  • df.describe(include='all') surfaces suspicious min/max values and category counts in one call.
  • A column's dtype is a diagnostic clue, not just metadata — "object" where you expect numbers is a red flag.

Module 2 · Intermediate

Mending Missing & Duplicate Data

⏱ 18 min🎯 Choose the right fix, not just any fix

Once you know where the damage is, the real skill is choosing how to repair it. Every strategy — dropping, filling, or interpolating — makes an assumption about why the data is missing. Get the assumption wrong and you quietly bias your analysis.

Analogy — Filling missing values is like road repair. dropna() closes the lane entirely. fillna(mean) is a quick pothole patch — fine for minor damage, dangerous if the road is falling apart. interpolate() is repaving based on the road's own trend on either side.
Missing Data Strategies
# Drop rows/columns
df.dropna(subset=['email'])          # drop rows missing a critical field
df.dropna(axis=1, thresh=len(df)*0.5)# drop columns that are mostly empty

# Fill with a value or statistic
df['age'].fillna(df['age'].median())   # robust to outliers
df['category'].fillna('unknown')       # explicit placeholder for text
df['reading'].fillna(method='ffill')   # carry the last known value forward

# Interpolate a trend
df['temperature'].interpolate(method='linear')

# Duplicates — normalize first, then drop
df['email'] = df['email'].str.strip().str.lower()
df.drop_duplicates(subset=['email'], keep='first')
Decision flow: the right missing-data fix depends on *why* the value is missing, not a default habit.
Comparisons
StrategyBest forRisk if misused
dropna()Small % missing, critical fieldsLoses rows silently, can shrink dataset a lot
fillna(mean/median)Numeric columns, random missingnessUnderstates variance, distorts distributions
ffill/bfillTime series, sensor logsWrong if the underlying value actually changed
interpolate()Ordered numeric trendsAssumes smooth change between points
Practical Exercise
Try it yourself

A hospital dataset has a blood_pressure column with 2% missing values scattered randomly, and a discharge_notes column that's 85% empty. What would you do with each column, and why?

blood_pressure: 2% random missingness on a numeric vital is a good candidate for fillna(median) — small enough not to meaningfully distort the distribution. discharge_notes at 85% empty is not a filling problem — it's a column that likely isn't consistently collected; consider dropping it or treating its presence as a separate boolean flag rather than trying to fill the text.

Common Misconceptions
✕"Always drop rows with any missing data." On real datasets this can silently discard a third of your rows and introduce bias if missingness isn't random.
✕"fillna(0) is always a safe default." Zero has meaning in most numeric columns (temperature, balance, score) — filling with 0 can fabricate a false data point.
Key Takeaways
  • Match the fix to *why* the value is missing — random noise, a broken sensor, or a genuinely inapplicable field each need a different answer.
  • Normalize text (strip().lower()) before deduplicating — otherwise "NY " and "ny" won't match.
  • Document every fill/drop decision; it's part of the analysis, not an invisible preprocessing step.

Module 3 · Advanced

Taming Types, Text & Outliers

⏱ 20 min🎯 Convert, extract, and judge extreme values

With missingness under control, the next layer is precision: making sure every column holds the type it claims to, text is normalized, and extreme values are understood rather than blindly removed.

Analogy — Converting types is like converting units in a recipe — grams to cups only works with the right formula, and getting it wrong doesn't throw an error, it just quietly ruins the dish. errors='coerce' is your safety net: it turns "unconvertible" values into NaN instead of crashing or guessing.
Type Conversion & Text Cleaning
# Safe numeric conversion
df['price'] = df['price'].str.replace('$','', regex=False).str.replace(',','', regex=False)
df['price'] = pd.to_numeric(df['price'], errors='coerce')

# Safe date conversion (mixed formats)
df['signup_date'] = pd.to_datetime(df['signup_date'], errors='coerce', dayfirst=False)

# Text normalization
df['state'] = df['state'].str.strip().str.upper()

# Regex extraction into new columns
df['area_code'] = df['phone'].str.extract(r'\((\d{3})\)')
Outlier Detection: the IQR method
Values beyond Q1 − 1.5×IQR or Q3 + 1.5×IQR are flagged as statistical outliers — not automatically deleted.
Q1, Q3 = df['income'].quantile(0.25), df['income'].quantile(0.75)
IQR = Q3 - Q1
lower, upper = Q1 - 1.5*IQR, Q3 + 1.5*IQR
outliers = df[(df['income'] < lower) | (df['income'] > upper)]
Comparisons
SituationLikely a real valueLikely a data error
CEO salary in an employee datasetYes — legitimate extreme
Age = 300Yes — entry error
Temperature = -999Yes — common "missing" sentinel value
Practical Exercise
Try it yourself

A delivery_days column has values like 3, 4, 5, 5, 6, and one row with 9999. Would you cap it, drop it, or investigate first — and what pandas call would you use to check?

Investigate first: df[df.delivery_days > 100] to inspect the full row — 9999 is a classic sentinel for "unknown," not a real delivery time. If it's confirmed as a placeholder, convert it to NaN rather than capping it as if it were a genuinely slow delivery.

Common Misconceptions
✕"Outliers are always errors and should be removed." Some outliers are the most important rows in the dataset — fraud detection and top-performer analysis often *are* the outliers.
✕"Regex is overkill for simple cleaning." A single str.extract() call often replaces dozens of lines of manual string slicing and is far less error-prone.
Key Takeaways
  • errors='coerce' turns bad conversions into visible NaNs instead of crashes or silent corruption.
  • IQR and z-score methods flag candidates — a human (or documented rule) still decides what to do with them.
  • Normalize text before comparing or grouping; casing and whitespace are the most common hidden category duplicates.

Module 4 · Expert

Building a Reusable Cleaning Pipeline

⏱ 17 min🎯 Turn one-off fixes into a repeatable process

Cleaning a dataset once is a task. Cleaning every new batch of data the same way, reliably, is engineering. This module turns your module 1–3 techniques into a single, testable, reusable function.

Analogy — A cleaning pipeline is an assembly line, not a single craftsman's workbench. Each station (missing values → duplicates → types → validation) does one job, in a fixed order, and passes the part to the next station — so anyone can run it and get the same result.
Chaining with .pipe() and functions
def handle_missing(df):
    df = df.copy()
    df['age'] = df['age'].fillna(df['age'].median())
    return df.dropna(subset=['email'])

def remove_duplicates(df):
    df['email'] = df['email'].str.strip().str.lower()
    return df.drop_duplicates(subset=['email'])

def fix_types(df):
    df['signup_date'] = pd.to_datetime(df['signup_date'], errors='coerce')
    return df

def validate(df):
    assert df['age'].between(0, 120).all(), "Impossible ages found"
    assert df['email'].str.contains('@').all(), "Malformed emails found"
    return df

clean_df = (raw_df
    .pipe(handle_missing)
    .pipe(remove_duplicates)
    .pipe(fix_types)
    .pipe(validate))
A pipeline is just functions chained through .pipe() — each stage does one job and hands off a clean copy.
Comparisons: apply() vs vectorized operations
ApproachSpeedWhen to use
df['x'] * 2 (vectorized)Fast — runs in optimized CWhenever a built-in operation exists
df['x'].apply(fn)Slower — loops in PythonOnly when logic can't be vectorized
Practical Exercise
Try it yourself

You merge orders with customers on customer_id and the row count of the result is larger than either input. What almost certainly happened, and how would you confirm it?

A many-to-many join: customer_id isn't unique in one or both tables, so matching rows multiply ("fan out"). Confirm with customers['customer_id'].duplicated().sum() and orders['customer_id'].duplicated().sum() before merging, or pass validate='many_to_one' to pd.merge() to raise an error if the assumption is violated.

Common Misconceptions
✕"Once it's clean, it's done." New data arrives with new mess — the value of a pipeline is that it runs the same checks every time, automatically.
✕"Merges always preserve row count." Duplicate keys on either side of a join silently multiply rows — always sanity-check the result's shape.
Key Takeaways
  • Wrap each cleaning concern in its own function and chain them with .pipe() for a readable, reusable pipeline.
  • Add assert checks at the end of the pipeline — cheap insurance against silent regressions.
  • Prefer vectorized operations over apply(); reach for apply() only when there's no vectorized equivalent.

Summary Notes

Cleaning data is a four-stage discipline: inspect before touching anything, repair missing and duplicate records with a documented, reasoned strategy, enforce correct types and normalize text so comparisons and math behave, and assemble everything into a pipeline with validation so the process is repeatable on the next messy file that lands on your desk. Outliers are signals to investigate, not defects to auto-delete.
